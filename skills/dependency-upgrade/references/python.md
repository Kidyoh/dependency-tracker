# Python

## Package manager

| Evidence | Manager |
|---|---|
| `uv.lock`, or `[tool.uv]` in `pyproject.toml` | uv |
| `poetry.lock`, or `[tool.poetry]` | poetry |
| `pdm.lock` | pdm |
| `Pipfile` | pipenv |
| `requirements*.txt` with a `requirements*.in` beside it | pip-tools (or `uv pip compile`) |
| `requirements*.txt` only, or bare `pyproject.toml` | pip |

Work inside the project's virtual environment. Create one (`python -m venv .venv` or `uv venv`) if none exists, and never install into the system interpreter.

## Commands

| Task | uv | poetry | pip |
|---|---|---|---|
| Install | `uv sync --all-extras --dev` | `poetry install` | `pip install -r requirements.txt` or `pip install -e ".[dev]"` |
| Outdated | `uv tree --outdated --depth 1` | `poetry show --outdated --top-level` | `pip list --outdated --format json` |
| Upgrade one | `uv add "<pkg>>=<ver>"` or `uv lock --upgrade-package <pkg>` | `poetry add "<pkg>@^<ver>"` or `poetry update <pkg>` | edit the pin, then reinstall |

When the constraint in `pyproject.toml` already allows the target version, only the lock needs to move (`uv lock --upgrade-package`, `poetry update`). When it does not, widen the constraint with `add`.

For pip-tools, edit the `.in` file and recompile (`pip-compile --upgrade-package <pkg>`); never hand-edit the compiled `.txt`. For a plain pinned `requirements.txt`, edit the one pin and keep the file's style, hashes excluded: a file with `--hash` lines must be regenerated by the tool that made it.

`pip list --outdated` shows transitive packages too. Direct dependencies are the ones named in the manifest.

## Finding the changelog

```
curl -s https://pypi.org/pypi/<pkg>/json | jq '.info.project_urls, .info.home_page'
```

Look for `Changelog`, `Release notes`, `Documentation` and `Source` in `project_urls`.

## Checks

Read `pyproject.toml`, `tox.ini`, `noxfile.py`, `Makefile` and CI. Typical set: `pytest`, a type checker (`mypy`, `pyright`), a linter (`ruff check`, `flake8`). Run pytest with `-x -q` while fixing, and the full run before committing.

Run the tests with warnings visible (`-W default`) once after each upgrade: `DeprecationWarning` from the upgraded package names what will break next, and belongs in the report.

## Things that go wrong

- **`requires-python`.** A new release may drop the Python version CI uses. Check `requires_python` in the PyPI JSON against the project's own `requires-python` and CI matrix.
- **Resolver conflicts.** When two packages cap a shared dependency differently, upgrade them as one unit or hold back. Do not delete a cap to force a resolution.
- **Big migrations** with their own guides and tools: pydantic 1 to 2 (`bump-pydantic`), SQLAlchemy 1.4 to 2.0, Django majors (read the release notes for each skipped version, run with `-W error::DeprecationWarning` first), NumPy 1 to 2 (`ruff` rule `NPY201`), pandas majors.
- **Compiled packages.** A new version may lack a wheel for the platform or Python version and fall back to a source build. If the install starts compiling and fails, treat it as an unsupported target and revert.
- **Type stubs.** `types-*` packages follow the package they describe; upgrade them together.
- **Django and Alembic migrations.** An ORM upgrade can generate new migrations. Run the project's migration check (`makemigrations --check`); a new migration caused only by the upgrade needs a human decision, so report it.
